# SQL Security Guide

## Principle: Parameterized Queries + Whitelist Validation

All SQL executed against DuckDB must use **parameterized queries** (`?` placeholders) for data values and **whitelist validation** for dynamic identifiers (table names, column names).

## Defense Layers

| Layer | Mechanism | Responsibility |
|-------|-----------|----------------|
| 1 | `validate_table_name()` | Validates table names against `ALLOWED_TABLES` |
| 2 | `?` placeholders | All user-supplied values go through parameterized queries |
| 3 | Read-only connections | Background tasks use read-only DB connections where feasible |

## ALLOWED_TABLES (database.py)

17 tables are whitelisted:

- `stocks`, `daily_prices`, `monthly_revenue`, `financials`, `valuations`
- `signals`, `guru_scores`, `strategy_config_history`
- `backtest_runs`, `backtest_positions`, `backtest_equity`
- `alert_settings`, `ingestion_tracker`, `operation_logs`, `alert_log`
- `portfolio`, `lots`

Add new tables to both `CREATE TABLE` and `ALLOWED_TABLES`.

## Rules

1. **No f-strings in SQL with user input.** Use `?` placeholders exclusively.
2. **Any dynamic table name must pass `validate_table_name()`.** This includes iteration variables (`for t in [...]`), function parameters, and any string that ends up as a table identifier.
3. **Column names in `ORDER BY`, `GROUP BY`, and WHERE clauses** should come from a whitelist or be hardcoded. Avoid interpolating user input into column position.
4. **`IN (...)` clauses** must use `?,?,?` placeholders generated by `", ".join("?" * len(items))`.

## Examples

### ✅ Safe: Parameterized query
```python
db.execute("SELECT * FROM stocks WHERE stock_id = ?", [stock_id])
```

### ✅ Safe: Whitelisted table name + parameterized WHERE
```python
tbl = validate_table_name(table_name)
db.execute(f"SELECT COUNT(*) FROM {tbl} WHERE trade_date >= ?", [min_date])
```

### ⚠️ UNSAFE: f-string with user input
```python
# NEVER DO THIS:
db.execute(f"SELECT * FROM {user_input} WHERE stock_id = '{stock_id}'")
```
